# 2026-10-12 A — 자를 바꿔도 같은 결론인가 + W&B 점검·백필

두 가지를 했다. 하나는 **지표 민감도 분석**(§1~3), 하나는 **W&B 기록 점검과 백필**(§4~5)이다.

지표 민감도는 개발 구간에 이미 저장된 예측만 다시 채점한 것이다. 모델을 새로 학습하지 않았고, 홀드아웃 정답·점수는 읽지 않았고, API 호출은 0회다. 설정은 실행 전에 [`reports/followup_checks/metric_robustness_protocol.json`](../../reports/followup_checks/metric_robustness_protocol.json)에 고정했다.

**결론부터.** 결론은 흔들리지 않았지만, **주장의 범위가 좁아졌다.** B0가 트리 모델을 앞서는 이유는 "더 좋은 예측"이 아니라 **공식 점수가 급등락을 4배로 치고 보합을 0으로 치기 때문**이다. 그 가중을 빼면(`plain_qwk`) 우위가 **−0.0018로 뒤집힌다.** 제출을 바꿀 이유는 없다 — 교수님 지표가 공식 지표이니 거기에 맞추는 게 맞다. 다만 발표에서 "B0가 더 좋은 모델"이 아니라 **"B0가 이 지표에서 가장 낫다"**로 말해야 한다.

---

## 1. 왜 이걸 했나

어제·오늘 실험에서 걸리는 게 하나 있었다. 기대 비용 디코딩(`lgb_cost`)은 **정확도 0.378, 방향 반대 11.7%**로 예측 품질이 전체 1위인데 **공식 점수는 0.346으로 최하위**였다. 보합으로 답을 피해서 그런 건데(60.8%), 그렇다면 "B0가 이긴다"는 결론이 **모델의 성질인지 자(尺)의 성질인지** 구분되지 않는다.

피어리뷰 체크리스트([`docs/final/TEAM_CHECKLIST.md`](../final/TEAM_CHECKLIST.md))에도 "지표: 공식 score, 동일 기간·집합" 항목이 있다. 다른 팀이 물어볼 만한 질문이라 미리 답을 만들어 두는 게 목적이었다.

## 2. 실험방법

[`scripts/oct12_metric_robustness.py`](../../scripts/oct12_metric_robustness.py)

저장돼 있던 개발 예측(train40) 18개 후보를 모았다. 규칙 계열 12개(B0, 10/10의 `L_*`·`C_*`·`V_*`·`S_B0`, 오늘의 `P1`)와 트리 계열 6개(`lgb_aggr`/`cost`/`ratio`, 가중 `wlgb_*`)다. B0는 세 파일에 모두 있으므로 **행 단위로 일치하는지 먼저 확인**했다(불일치면 중단).

자 다섯 개를 실행 전에 정했다. 전부 `1 − Σw·O / Σw·E` 형태를 유지해 **0이 우연**이 되게 했다.

| 자 | 오답 비용 `W[정답 i, 예측 j]` | 뜻 |
|---|---|---|
| `official` | `(i−j)² × |i−2|²` | 공식 지표 (`src/data.py:50`) |
| `flat_credit` | 같지만 **정답이 보합인 행에 `(i−j)²`** | 보합을 맞히면 점수를 줌 |
| `linear` | `|i−j| × |i−2|²` | 멀리 틀려도 덜 깎임 |
| `plain_qwk` | `(i−j)²` | **급등락 4배 가중 없음** |
| `extreme_only` | 정답이 급등락인 행만 `(i−j)²` | 급등락 날만 셈 |

정확도와 방향 적중률도 같이 적었다.

**미리 적어 둔 한계**: 트리·규칙 후보들은 내부 손잡이(scale, δ, τ, 경계)를 **공식 점수로 골랐다.** 그러니 이건 "다른 자로 다시 학습했다면 어땠을까"가 아니라 **"이미 굳은 예측이 다른 자로 재면 어떻게 줄 서나"**다.

### 3-1. 규칙 계열 12개는 사실상 같은 모델이다

어떤 자로 재도 12개가 **폭 0.0014~0.0027 안에** 다 들어온다. 방향 적중률은 P1(0.5552)만 빼고 **12개가 전부 0.5509로 똑같다.** 10/10의 텍스트·기업별 후보들이 건드린 건 **"얼마나 크게 움직일지" 경계뿐이고 방향은 하나도 안 바꿨다**는 뜻이다. 그래서 B0의 순위가 자에 따라 3위~8위로 움직이지만, **이건 순위 변동이 아니라 노이즈다.**

여기서 짚어야 할 게 하나 있다. **B0는 애초에 개발 평균 1위가 아니었다.** 공식 점수로 P1(0.4485), L_R(0.4471), L_NR(0.4469)이 B0(0.4469)보다 높거나 같다. B0가 남은 건 평균이 제일 높아서가 아니라 **사전 고정한 채택 기준**(평균 +0.005, 3폴드 이상, fold4 비음수, bootstrap 하한 > 0) 때문이다. P1의 +0.0017은 기준의 1/3이고 bootstrap 하한이 −0.0002다. 발표에서 "왜 평균이 더 높은 후보를 안 썼나"를 물으면 이게 답이고, **기준이 노이즈 수준 1위를 거르는 쪽으로 작동한 예**다.

### 3-2. 본론: B0의 우위는 급등락 가중에서 나온다

B0와 **트리 계열 중 가장 좋은 것**의 차이를 자별로 보면 이렇다.

| 자 | B0 | 최고 트리 | 차이 |
|---|---:|---:|---:|
| `official` | 0.4469 | 0.4256 | **+0.0213** |
| `flat_credit` | 0.4032 | 0.3873 | +0.0159 |
| `extreme_only` | 0.5317 | 0.5240 | +0.0077 |
| `linear` | 0.3541 | 0.3450 | +0.0091 |
| `plain_qwk` | 0.3023 | 0.3041 | **−0.0018** |

급등락 가중(`|i−2|²`)을 빼면 **차이가 사라지고 부호가 뒤집힌다.** 즉 갭 규칙이 LightGBM을 이기는 건 "예측이 더 좋아서"가 아니라, **공식 지표가 급등락을 4배로 치고 보합을 0으로 치는 구조에 갭 규칙이 잘 맞아서**다.

예측 품질 자체로 보면 순서가 거의 반대다. `lgb_cost`는 **정확도 0.378 대 B0의 0.262**로 어떤 자를 쓰든 훨씬 정확하다. 공식 점수에서 꼴찌인 건 60.8%를 보합으로 답하는데 **공식 지표가 맞춘 보합에 0점을 주기 때문**이고, `flat_credit`으로 보합에 점수를 주면 격차가 0.0213 → 0.0159로 줄어든다. 그래도 B0가 앞서는데, 보합을 맞혀서 받는 점수보다 급등락 가중에서 잃는 게 더 크기 때문이다.

### 3-3. 그래서 발표에서 어떻게 말해야 하나

**제출은 바꿀 이유가 없다.** 평가 지표가 공식 지표이니 거기에 맞춘 모델을 내는 게 맞고, 홀드아웃도 10/9에 이미 B0로 확정했다. 바뀌는 건 **말하는 범위**다.

- (×) "갭 규칙이 머신러닝보다 좋은 모델이다"
- (○) "갭 규칙이 **이 지표에서** 가장 낫다. 지표가 급등락을 4배로 치는 구조라서 그렇고, 그 가중을 빼면 LightGBM과 사실상 같다."
- (○) "정확도만 보면 LightGBM이 0.378로 더 높다. 우리는 **정확도를 재는 과제가 아니라서** 그걸 안 골랐다."

이게 "조건 없는 0.6 비교를 피하라"는 체크리스트 항목과도 맞는 태도다.

## 5. 백필 실행

### 방법

재은 요청으로 빠진 32개를 전부 올렸다([`scripts/wandb_backfill.py`](../../scripts/wandb_backfill.py)).

올린 값은 **전부 커밋된 `reports/` 산출물에서 읽어온 것**이다. 아무것도 다시 계산하지 않았고 모델을 다시 학습하지 않았다. 그래서 백필된 run은 해당 보고서 파일이 말하는 것과 정확히 같은 말을 한다.

W&B는 run에 **만든 시각**을 찍기 때문에 그냥 올리면 32개가 모두 오늘 한 일처럼 보인다. 그래서 세 군데에 실제 실험일을 박았다: run 이름 앞(`2026-10-10_…`), 태그 `orig:2026-10-10`, `config.original_date`. 전부 `backfill` 태그를 달았고, 원본 파일의 sha256 앞 16자리를 `config.source_files`에 넣었다.

예측 행과 원자료는 올리지 않았다(`lab/tracking.py`의 기존 정책과 같음). 올린 건 집계 지표와 표다.

**올리기 전에 고친 것 하나.** 처음 돌린 dry-run에서 **B0가 `not_adopted`로 태그됐다.** `reports/final_study/selection.json`에는 도전자(T1·X1·X2·A1)만 결정 행이 있고 B0는 없어서 기본값으로 떨어진 것이다. 제출 모델이 공유 워크스페이스에서 "미채택"으로 보이면 정반대로 읽히므로 `submitted` 태그로 분리했다.

### 올린 것

| 종류 | 수 | job_type |
|---|---:|---|
| 후보 모델 (fold별 점수 있음) | 22 | `cv_backfill` |
| 점검 (후보 점수 없음) | 9 | `audit_backfill` |
| 홀드아웃 1회 | 1 | `holdout_backfill` |
| **합계** | **32** | |

실험일별로는 10/09 7개, 10/10 10개, 10/11 2개, 10/12 13개다. 태그별로는 `submitted` 1개(B0), `not_adopted` 21개, `audit` 9개, `holdout` 1개다.

후보 22개는 `final_study` 5개(A1·B0·T1·X1·X2), `oct10_extension` 10개(`L_*`·`C_*`·`V_*`·`S_B0`), `followup_p1` 1개(P1), `followup_cost_decode` 6개다. B0는 여러 집단에서 기준으로 쓰이므로 **`final_study`에서 한 번만** 올리고 나머지 집단에서는 중복 생성하지 않았다.

점검 9개는 강의 반영 검증(순열·ALE·SHAP·텍스트 품질), 10/11 진단(e1·e3·e4), LLM 방향 선별, LightGBM 갭 순열·ALE, 수집률, 제목 신규성 선별, 집계 보완, T1 선별, 지표 민감도다.

### 확인

업로드 후 W&B API로 직접 다시 읽어 확인했다.

- `backfill` 태그 run **32개**, 프로젝트 전체 run은 95 → **127개**
- `2026-10-09_final_study_B0` score **0.446866**, fold4 **0.515419** — 기준값과 일치, 태그 `submitted`
- `2026-10-12_followup_p1_P1` score **0.448532**, fold4 0.515407 — `p1_decision.json`과 일치
- `2026-10-12_followup_cost_decode_lgb_cost` score **0.345979** — 일치
- `2026-10-09_holdout_B0` score **0.596716** — `holdout_metrics.csv`와 일치, 태그 `holdout`

### 남는 한계

run의 생성 시각은 전부 백필한 날짜다. **실제 실험일은 run 이름·`orig:` 태그·`config.original_date`로만 구분된다.** W&B 목록을 시간순으로 보면 32개가 한 덩어리로 보이므로, 날짜별로 보려면 `orig:` 태그로 걸러야 한다. 이 점을 발표나 피어리뷰에서 물어보면 숨기지 말고 "기록은 실험 당일 `reports/`에 남겼고 W&B 업로드만 10/12에 소급했다"고 답하면 된다. git 로그가 그 주장을 뒷받침한다.

## 6. 검증과 한계

[`tests/test_oct12_followup.py`](../../tests/test_oct12_followup.py) 10개 통과(기존 9개 + 1개 추가).

- **`official` 자가 진짜 공식 지표인지**: 모든 fold·후보에서 `chance_corrected(…, official)`이 `src.score`와 1e-12 미만 차이. 이게 틀리면 비교 전체가 무의미해지므로 먼저 확인했다.
- **다섯 자 모두 0이 우연인지**: 한 등급만 계속 찍으면 다섯 자 전부에서 정확히 0이 나온다.
- B0 예측이 세 파일에서 행 단위로 일치하는지 실행 중 assert로 확인.

**한계.** §2에 미리 적은 대로, 후보들의 내부 손잡이는 공식 점수로 골랐으므로 이건 "굳은 예측을 다른 자로 재면 어떻게 줄 서나"다. 다른 자로 처음부터 학습했다면 트리 계열이 `plain_qwk`에서 더 벌어졌을 수도 있다. 그리고 이 숫자들도 반복해서 본 개발 구간에서 나왔다. 채택은 없고 제출은 B0 그대로다.
